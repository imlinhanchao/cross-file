## 1. 一句话定位

**任意两台设备之间，扫码即传，端到端加密，服务器不存一个字节；500MB 级临时文件像发一条消息。**

四根支柱，缺一不可：**零安装接收端**（浏览器打开就能收）、**内容不落任何服务器**、**跨网络可达**、**用完即走**（无账号、无历史、无留存）。

---

## 2. 要解决的问题与不解决的问题

**做**：临时、较大、一次性的文件传输。典型是「把手机里一段 300MB 的视频发给旁边的人」「跨网络把一个 500MB 的设计稿发给没有装任何 App 的客户」。

**不做（v1 非目标，明确写进 README）**：

| 非目标 | 原因 |
|---|---|
| 云盘 / 长期存储 / 历史记录 | 与「不留存」冲突；那是 WeTransfer 的赛道 |
| 账号、好友、通讯录、群组 | 无身份是卖点，不是缺陷 |
| 文件夹 / 目录同步 | 协议与 UI 复杂度翻倍；Syncthing 已覆盖 |
| 文本 / 剪贴板互传 | v1.x 候选，会稀释大文件定位 |
| 无外网局域网（②） | 需要本地信令 + WebCrypto/WASM 兜底 + 原生壳，v1.x 再议 |
| 纯邻近（③，BLE/AWDL/Wi-Fi Direct） | 跨平台基本不可得，留作长期研究 |
| 跨会话续传 | 需要服务端持久化任何状态，违背 D1 |
| 多文件并发传输 | 顺序队列已够用，并发会平分上行 |
| 端到端「阅后即焚」以外的留存 | 没有留存 |

## 3. 已定决策（D1–D18，变更须写 ADR）

| # | 决策 | 关键理由 |
|---|---|---|
| D1 | **同步 P2P**：收发双方必须同时在线，服务器不存内容，连内存缓冲都不写 | 「不留存」的唯一诚实实现 |
| D2 | 路径阶梯 **④跨网打洞 → ①同网直连 → ⑤TURN 中继**，由 ICE 自然优先，UI 显示实际路径 | 直连最快最省；中继兜底 |
| D3 | **密钥只在二维码/链接 fragment 里**，永不发往服务器 | 服务器零知识的基础 |
| D4 | **应用层 AES-256-GCM** 流式加密，密文进数据通道 | 即使信令被篡改也读不到内容 |
| D5 | 6 位码路径 = **房间定位符 + 发送方批准 + 双方比对 4 个 emoji SAS** | 码装不下密钥，SAS 补认证 |
| D6 | 发送方建房间；接收方扫码/点链接/输码加入；**最多 4 个接收方**（官方实例 2 个），加入需发送方批准，可移除 | 多接收方是真实需求（自己的多设备 / 分给几个人） |
| D7 | **发送方关闭即销毁房间**；异常离线最迟 30 分钟被清理；空闲计时由信令活动续期 | 保留「想挂多久挂多久」，又不留无人看守的房间 |
| D8 | **发送方是会话宿主，必须在线**；Web 端锁屏/刷新会断，原生壳用前台服务保活 | D1 的必然代价，写进产品说明 |
| D9 | 文件：多选；**单文件 500MB 硬顶**，单会话总量 2GB，同时传输 1 个（顺序队列） | 上限是产品参数，不是营销点 |
| D10 | **会话内断点续传**：通道断开后 60 秒内重连成功即从缺片处续传 | 移动端断网/锁屏是常态 |
| D11 | **接收端零安装（浏览器）是硬承诺**，但按接收端能力动态降级（见 §6） | 零安装是最大差异化，但不能对 iPhone 撒谎 |
| D12 | 平台：Web 全功能；桌面/手机用 **Tauri 2** 壳；鸿蒙走浏览器（ArkWeb 待实测） | 一套 TS 核心 + 三壳，鸿蒙免开发 |
| D13 | 官方实例 = **免费信令 + 限速中继兜底**；自托管优先；开源 MIT | 不做免费 CDN，不靠它赢 |
| D14 | **无账号、无持久日志、无分析埋点、无 cookie 追踪** | 「不记录」的可验证版本 |
| D15 | 许可证 **MIT** | 最大采纳度 |
| D16 | 接收方加入时上报**能力包**（浏览器/平台/是否原生壳/是否有文件系统 API/内存/配额），发送方按规则计算软硬上限并提示 | 你 Q2 的「动态调整 + 发送方提示」 |
| D17 | 完整性：逐片 GCM 认证 + 传输结束的**全文件 SHA-256** 双向校验 | 缺片、乱序、截断、静默损坏全部可发现 |
| D18 | 多接收方 = **顺序队列 + 文件×人勾选矩阵** | 同一文件发给 N 人就是发 N 次；顺序不打满上行 |

## 4. 典型旅程

**发送方（宿主）**
1. 打开 Web / App → 点「发送」→ 本地生成 roomId + 32 字节密钥 → 创建房间。
2. 屏幕出现：二维码 + 短链接 + 6 位数字码；名单区「等待接收方」。
3. 接收方加入 → 弹出「是否允许加入？」→ 批准（6 位码路径还要比对 4 个 emoji）。
4. 拖入/选择文件 → 勾选这次发给谁 → 点发送 → 队列逐个执行，显示路径标签（局域网直连 / 直连 / 中继）、速度、进度。
5. 全部完成或点「结束房间」→ 房间立即销毁、密钥清零。

**接收方（零安装）**
1. 扫码/点链接 → 浏览器打开 → 看到「XXX 想给你发送 N 个文件（X MB）」。
2. 确认接收 → 若能力不足（如 iPhone Safari 收 400MB）→ 明确警告「可能无法保存，建议让对方改用 App 或电脑」。
3. 传输 → 完成后由浏览器/壳保存；关闭页面即走。

## 5. 隐私承诺（对外文案已定稿，改字要过审）

> **服务器不存一个字节。** 文件在你的设备和对方的设备之间端到端加密传输，服务器只转发密文，密钥只存在于二维码或链接里，从不发送到服务器。
> **不记录。** 没有账号，没有历史，没有分析埋点，没有持久日志。会话一结束，服务器内存里的房间状态立即清除。
> **诚实说明。** 为了建立连接，服务器能看到双方的 IP 地址、房间存在的时间、以及经过中继的流量大小；自托管可以自己验证这一点。

威胁模型与更细的技术前提见 `02-protocol.md` §2。

## 6. 平台能力矩阵与动态限制（D11 / D16）

接收方加入时通过信令上报能力包；**发送方在发送前、接收方在确认前各看到一次基于该能力包的限制提示**。阈值是一张可配置表，v1 用保守初值，后续用实测校准。

| 接收端 | 保存方式 | 软上限（超过提示/建议装壳） | 硬上限（拒绝） |
|---|---|---|---|
| 原生壳（桌面/手机） | 直接写盘 | 500MB | 500MB |
| Chrome / Edge 桌面 | 文件系统 API 流式写盘 | 500MB | 500MB |
| Safari 桌面 | Service Worker 流式下载（自研，Safari 15.4+）→ 兜底内存 Blob | 250MB（实测通过后可放宽至 500MB） | 500MB（需二次确认风险） |
| Firefox 桌面 | 内存 Blob | 250MB | 500MB（需二次确认风险） |
| Android 浏览器 | 内存 Blob | 150MB | 500MB（需二次确认风险） |
| iOS（所有浏览器均为 WebKit） | Service Worker 流式下载（待 iOS 实机验证）→ 兜底内存 Blob | 100MB（实测通过后可放宽） | 500MB（强烈建议装 App） |
| 未知/识别失败 | 保守 | 150MB | 500MB（需二次确认风险） |

规则：超过软上限 → 发送方界面弹提示「该接收方为 iPhone Safari，超过 100MB 可能无法保存」，可选「仍要发送 / 换一个接收方 / 建议对方装 App」；超过硬上限 → 拒绝。接收方确认页同样展示风险。

> 2026-11-24 更新：Safari 桌面（macOS 27）与 iOS 27.2 模拟器 Safari 均经 TURN 接收 100 MB，双方 SHA-256 一致；接收端超软上限的风险提示由能力门禁实现。保存点击（Safari 需用户手势）与 iOS 落盘仍待人工，故上限暂不放宽；Safari 桌面经直连接收 500 MB 并完成哈希（未点保存）已验证内存侧可行。
> 阈值初值依据见附录 A / 附录 C。Safari 15.4+ 的 Service Worker 流式下载已确认存在（WebKit bug 202142），但 StreamSaver.js 在 Safari 不可用、需自研；M1/M2 实测通过后把 Safari/iOS 软上限放宽到 500MB。接收端保存层按能力在 `native / fs / sw / blob` 四种策略里选（见 `02-protocol.md` §6.8）。

## 7. 与竞品的关系（一句话版）

- **LocalSend**：局域网强者、开源，但主要靠两端装 App；我们的差异是跨网络 + 零安装接收 + 零服务器存储。
- **PairDrop / FilePizza**：浏览器同类，但依赖其 TURN 且要信任其服务器；我们密钥在 fragment、可自托管。
- **Wormhole / Send Anywhere / WeTransfer**：跨网络只靠落盘，和 D1 冲突。
- **Blip**：明确不做网页接收链接，正是我们切的缝。

详细对照见附录 B。

## 8. 验收标准（v1 必须全部通过）

| # | 场景 | 通过标准 |
|---|---|---|
| AC1 | Chrome↔Chrome 同一局域网，500MB | 传完、SHA-256 一致、平均 ≥60 Mbps、UI 显示「局域网直连」 |
| AC2 | Chrome↔Chrome 跨网络（仅 TURN），500MB | 传完、哈希一致、UI 显示「中继」；10 Mbps 带宽下 <10 分钟 |
| AC3 | 传输中断续传 | 传输到 50% 强制断开通道，60 秒内重连，只重传缺失分片，最终哈希一致 |
| AC4 | Chrome 发送 → iPhone Safari 接收 100MB | 传完并可保存；500MB 时出现分级提示且拒绝/警告行为符合 §6 |
| AC5 | 6 位码加入 | 输码 → 批准 → 双端显示 4 emoji 一致 → 传输成功；emoji 不一致时中止 |
| AC6 | 多接收方 | 2 个接收方顺序到达，文件×人矩阵正确，队列不并发 |
| AC7 | 房间生命周期 | 发送方点结束 → 双方立即断开、服务器内存房间消失；发送方强杀进程 → ≤30 分钟清理 |
| AC8 | 零存储审计 | 服务器进程无数据库/无文件写入；`strace -f -e trace=openat,write` 无文件内容落盘；无请求日志 |
| AC9 | 三端可选 | 桌面壳（Chrome 内核）与手机壳（Tauri）各自完成 AC1 的 500MB 用例 |

性能基线（记录用途，不设死线）：同 Wi-Fi 500MB ≤ 60 秒为达标，≤30 秒为优秀。

## 9. 术语

- **房主 / 宿主（host）**：发起会话的发送方，房间生命周期由它掌握。
- **接收方（guest）**：通过二维码/链接/数字码加入的设备。
- **roomId**：16 字节随机标识，可公开。
- **roomKey**：32 字节会话根密钥，只在二维码/链接 fragment 或经 SAS 认证后的通道里出现。
- **路径标签**：局域网直连 / 直连 / 中继，来自 ICE 选中候选对的类型。
- **SAS**：Short Authentication String，由双方 DTLS 指纹派生、人工比对的短串，本产品用 4 个 emoji 表示。

1. 文档整体是否认可（尤其 §2 非目标、§6 阈值初值）。
