## 1. 一句话定位

**任意两台设备之间，扫码即传，端到端加密，服务器不存一个字节；500MB 级临时文件像发一条消息。**

四根支柱，缺一不可：**零安装接收端**（浏览器打开就能收）、**内容不落任何服务器**、**跨网络可达**、
**用完即走**（无账号、无历史、无留存）。

---

## 2. 要解决的问题与不解决的问题

**做**：临时、较大、一次性的文件传输。典型是「把手机里一段 300MB 的视频发给旁边的人」「跨网络把一个
500MB 的设计稿发给没有装任何 App 的客户」。

**不做（v1 非目标，明确写进 README）**：

| 非目标 | 原因 |
|---|---|
| 云盘 / 长期存储 / 历史记录 | 与「不留存」冲突；那是 WeTransfer 的赛道 |
| 账号、好友、通讯录、群组 | 无身份是卖点，不是缺陷 |
| 文件夹 / 目录同步 | 协议与 UI 复杂度翻倍；Syncthing 已覆盖 |
| 文本 / 剪贴板互传 | v1.x 候选，会稀释大文件定位 |
| 无外网局域网（②） | 需要本地信令 + WebCrypto/WASM 兜底 + 原生壳，v1.x 再议 |
| 纯邻近（③，BLE/AWDL/Wi-Fi Direct） | 跨平台基本不可得，留作长期研究 |
| 跨会话续传 | 需要服务端持久化任何状态，违背 D1 |
| 端到端「阅后即焚」以外的留存 | 没有留存 |

> 2026-11-26 补充：房间内互传（任意成员之间收发，D19）**仍然是短命、无身份的会话**——没有账号、没有历史、
> 成员关系只存在于房间存续期间，因此不构成「群组」能力；它只是把同一次会话里的收发方向放开。

## 3. 已定决策（D1–D25，变更须写 ADR）

| # | 决策 | 关键理由 |
|---|---|---|
| D1 | **同步 P2P**：收发双方必须同时在线，服务器不存内容，连内存缓冲都不写 | 「不留存」的唯一诚实实现 |
| D2 | 路径阶梯 **④跨网打洞 → ①同网直连 → ⑤TURN 中继**，由 ICE 自然优先，UI 显示实际路径 | 直连最快最省；中继兜底 |
| D3 | **密钥只在二维码/链接 fragment 里**，永不发往服务器 | 服务器零知识的基础 |
| D4 | **应用层 AES-256-GCM** 流式加密，密文进数据通道 | 即使信令被篡改也读不到内容 |
| D5 | 6 位码路径 = **房间定位符 + 管理员批准 + 双方比对 4 个 emoji SAS** | 码装不下密钥，SAS 补认证 |
| D6 | **管理员建房间**；成员扫码/点链接/输码加入；**最多 4 个成员**（官方实例 2 个），加入需管理员批准，可移除；**邀请权只属于管理员**（UI 约束） | 多成员是真实需求（自己的多设备 / 分给几个人） |
| D7 | **房间销毁**：阶段 1 管理员关闭即销毁；阶段 2 管理员离开时管理权自动移交给最早加入的在线成员，最后一人离开才销毁（D24）；异常离线最迟 30 分钟被清理；空闲计时由信令活动续期 | 保留「想挂多久挂多久」，又不留无人看守的房间 |
| D8 | **管理员是会话锚点，必须在线**（阶段 1）；阶段 2 管理权可移交，房间不再绑定单台设备；Web 端锁屏/刷新会断，原生壳用前台服务保活 | D1 的必然代价，写进产品说明 |
| D9 | 文件：多选；**单文件 500MB 硬顶**，**每个发送方**单会话总量 2GB；**同一对设备同时传 1 个**（方向不限），不同对可并发（D19） | 上限是产品参数，不是营销点 |
| D10 | **会话内断点续传**：通道断开后 60 秒内重连成功即从缺片处续传；双方都可用重连令牌回来 | 移动端断网/锁屏是常态 |
| D11 | **接收端零安装（浏览器）是硬承诺**，但按接收端能力动态降级（见 §6） | 零安装是最大差异化，但不能对 iPhone 撒谎 |
| D12 | 平台：Web 全功能；桌面/手机用 **Tauri 2** 壳；鸿蒙走浏览器（ArkWeb 待实测） | 一套 TS 核心 + 三壳，鸿蒙免开发 |
| D13 | 官方实例 = **免费信令 + 限速中继兜底**；自托管优先；开源 MIT | 不做免费 CDN，不靠它赢 |
| D14 | **无账号、无持久日志、无分析埋点、无 cookie 追踪** | 「不记录」的可验证版本 |
| D15 | 许可证 **MIT** | 最大采纳度 |
| D16 | 接收方加入时上报**能力包**（浏览器/平台/是否原生壳/是否有文件系统 API/内存/配额），发送方按规则计算软硬上限并提示；v2 下能力包广播给房间所有人，仍按接收方 caps 计算 | 你 Q2 的「动态调整 + 发送方提示」 |
| D17 | 完整性：逐片 GCM 认证 + 传输结束的**全文件 SHA-256** 双向校验 | 缺片、乱序、截断、静默损坏全部可发现 |
| D18 | 多成员 = **顺序队列 + 文件×成员勾选矩阵**（按发送者各自维护） | 同一文件发给 N 人就是发 N 次；顺序不打满上行 |
| D19 | **任意成员互传**：阶段 1 管理员↔成员双向（每对串行），阶段 2 任意成员之间；**收方 `accept` 即授权**，不需要管理员逐次批准 | 接收方也要能回传；房间内任意两台设备都应能互传 |
| D20 | **S 广播成员列表**（id/显示名/caps/是否管理员/在线状态），并在**任意两个成员之间转发信令**；S 仍零存储、不落盘 | mesh 必须让成员互相可见、可建连；S 本来就持有成员表 |
| D21 | **设备显示名**：默认 `平台 · 4 位代号`，入房前与会话中可改，1–16 个 Unicode 码点，重名自动加后缀；昵称本地记忆（Web 与原生壳 webview 的 `localStorage`），跨房间复用，可「忘记」 | 3 台以上设备时无法靠序号认人；昵称不是账号 |
| D22 | **协议 v2 不兼容旧端**：`PROTOCOL_VERSION = 2`，旧页面连接收到 `VERSION_MISMATCH` 并提示刷新；不写兼容层 | 接收方是扫码即用的零安装用户，版本分裂比强升级更伤；旧端明确报错而非静默失败 |
| D23 | **两阶段路线**：阶段 1 = 双向 1:1（管理员↔成员）+ 统一 Room 页；阶段 2 = mesh 懒建连 + 管理权移交；协议 v2 一次定义到位 | 阶段 1 先验证回传链路与 UI，阶段 2 再放开成员之间；协议改两次不划算 |
| D24 | **管理权自动移交**（阶段 2）：管理员离开时把管理权交给最早加入的在线成员，最后一人离开才销毁房间 | 「进入就能互传」不能因为管理员离开而中断 |
| D25 | **服务端 = Go 单二进制**（ADR 0011）：一个静态二进制内嵌 Web 静态资源、`/v1/ws` 信令与 TURN（pion/turn），协议 v2 与客户端零改动；服务器不再需要 Node 运行时与独立 coturn | 一个进程代替两个、内存/体积/发布/审计都更小；信令本身就是小状态机，替换成本低 |

## 4. 典型旅程

**创建房间（管理员）**
1. 打开 Web / App → 首页点「创建房间」→ 本地生成 roomId + 32 字节密钥 → 房间建立。
2. 屏幕出现：二维码 + 短链接 + 6 位数字码；成员区「等待成员加入」。
3. 成员加入 → 弹出「是否允许加入？」→ 批准（6 位码路径还要比对 4 个 emoji）。
4. 拖入/选择文件 → 勾选这次发给谁 → 点发送 → 队列逐个执行，显示路径标签（局域网直连 / 直连 / 中继）、
   速度、进度。
5. 全部完成或点「结束房间」→ 房间立即销毁、密钥清零。

**成员加入（零安装）**
1. 扫码/点链接/输码 → 浏览器打开 → 看到房间成员与「等待对方发送」。
2. 对方发来文件 → 看到「XXX 想给你发送 N 个文件（X MB）」→ 确认接收 → 能力不足时明确警告
   （如 iPhone Safari 收 400MB）→ 传输 → 由浏览器/壳保存。
3. 想回传：在同一个 Room 页点「选择文件」→ 发送给管理员（或对方）→ 对方确认后开始传输，进度与
   管理员发来的方向共用同一个房间视图。

**双向/多人（阶段 1 范围）**
- 同一对设备一次只跑一条传输；正向传输中发起反向 → 排队，等前一条完成后自动开始；
- 两个成员之间互传在阶段 2 开放；阶段 1 的每对传输仍以管理员为一端。

## 5. 隐私承诺（对外文案已定稿，改字要过审）

> **服务器不存一个字节。** 文件在你的设备和对方的设备之间端到端加密传输，服务器只转发密文，密钥只存在于
> 二维码或链接里，从不发送到服务器。
> **不记录。** 没有账号，没有历史，没有分析埋点，没有持久日志。会话一结束，服务器内存里的房间状态立即清除。
> **诚实说明。** 为了建立连接，服务器能看到双方的 IP 地址、房间存在的时间、以及经过中继的流量大小；
> 房间内互传时还能看到房间里有哪些设备、它们的显示名和平台，以及谁在跟谁建立连接。自托管可以自己验证这一点。

威胁模型与更细的技术前提见 `02-protocol.md` §2。

## 6. 平台能力矩阵与动态限制（D11 / D16）

接收方加入时通过信令上报能力包（v2 下由 S 广播给房间内所有人）；**发送方在发送前、接收方在确认前各看到
一次基于该能力包的限制提示**。阈值是一张可配置表，v1 用保守初值，后续用实测校准。
发送方可能是任意成员（Web、桌面壳、手机壳），规则不变：**始终按接收方的 caps 计算**。

| 接收端 | 保存方式 | 软上限（超过提示/建议装壳） | 硬上限（拒绝） |
|---|---|---|---|
| 原生壳（桌面/手机） | 直接写盘 | 500MB | 500MB |
| Chrome / Edge 桌面 | 文件系统 API 流式写盘 | 500MB | 500MB |
| Safari 桌面 | Service Worker 流式下载（自研，Safari 15.4+）→ 兜底内存 Blob | 250MB（实测通过后可放宽至 500MB） | 500MB（需二次确认风险） |
| Firefox 桌面 | 内存 Blob | 250MB | 500MB（需二次确认风险） |
| Android 浏览器 | 内存 Blob | 150MB | 500MB（需二次确认风险） |
| iOS（所有浏览器均为 WebKit） | Service Worker 流式下载（待 iOS 实机验证）→ 兜底内存 Blob | 100MB（实测通过后可放宽） | 500MB（强烈建议装 App） |
| 未知/识别失败 | 保守 | 150MB | 500MB（需二次确认风险） |

规则：超过软上限 → 发送方界面弹提示「该接收方为 iPhone Safari，超过 100MB 可能无法保存」，可选
「仍要发送 / 换一个接收方 / 建议对方装 App」；超过硬上限 → 拒绝。接收方确认页同样展示风险。

> 2026-11-24 更新：Safari 桌面（macOS 27）与 iOS 27.2 模拟器 Safari 均经 TURN 接收 100 MB，双方 SHA-256
> 一致；接收端超软上限的风险提示由能力门禁实现。保存点击（Safari 需用户手势）与 iOS 落盘仍待人工，故上限
> 暂不放宽；Safari 桌面经直连接收 500 MB 并完成哈希（未点保存）已验证内存侧可行。
> 阈值初值依据见附录 A / 附录 C。Safari 15.4+ 的 Service Worker 流式下载已确认存在（WebKit bug 202142），
> 但 StreamSaver.js 在 Safari 不可用、需自研；M1/M2 实测通过后把 Safari/iOS 软上限放宽到 500MB。接收端保存层
> 按能力在 `native / fs / sw / blob` 四种策略里选（见 `02-protocol.md` §6.9）。

## 7. 与竞品的关系（一句话版）

- **LocalSend**：局域网强者、开源，但主要靠两端装 App；我们的差异是跨网络 + 零安装接收 + 零服务器存储。
- **PairDrop / FilePizza**：浏览器同类，但依赖其 TURN 且要信任其服务器；我们密钥在 fragment、可自托管。
- **Wormhole / Send Anywhere / WeTransfer**：跨网络只靠落盘，和 D1 冲突。
- **Blip**：明确不做网页接收链接，正是我们切的缝。

详细对照见附录 B。

## 8. 验收标准（阶段 1 必须全部通过；AC1–AC9 为原 v1 基线）

| # | 场景 | 通过标准 |
|---|---|---|
| AC1 | Chrome↔Chrome 同一局域网，500MB | 传完、SHA-256 一致、平均 ≥60 Mbps、UI 显示「局域网直连」 |
| AC2 | Chrome↔Chrome 跨网络（仅 TURN），500MB | 传完、哈希一致、UI 显示「中继」；10 Mbps 带宽下 <10 分钟 |
| AC3 | 传输中断续传 | 传输到 50% 强制断开通道，60 秒内重连，只重传缺失分片，最终哈希一致 |
| AC4 | Chrome 发送 → iPhone Safari 接收 100MB | 传完并可保存；500MB 时出现分级提示且拒绝/警告行为符合 §6 |
| AC5 | 6 位码加入 | 输码 → 批准 → 双端显示 4 emoji 一致 → 传输成功；emoji 不一致时中止 |
| AC6 | 多成员 | 2 个成员顺序到达，文件×成员矩阵正确，队列不并发 |
| AC7 | 房间生命周期 | 管理员点结束 → 双方立即断开、服务器内存房间消失；管理员强杀进程 → ≤30 分钟清理 |
| AC8 | 零存储审计 | 服务器进程无数据库/无文件写入；`strace -f -e trace=openat,write` 无文件内容落盘；无请求日志 |
| AC9 | 三端可选 | 桌面壳（Chrome 内核）与手机壳（Tauri）各自完成 AC1 的 500MB 用例 |
| AC10 | 双向 1:1 | 管理员↔成员各方向 10MB/500MB，哈希一致，路径标签正确；反向传输同样要收方确认 |
| AC11 | 同一对排队 | 正向传输中发起反向 → 反向排队等待，不并发；前一条完成后自动开始 |
| AC12 | 双向续传 | 两个方向各自中途断线 → 60 秒内重连 → 只补缺失分片 → 哈希一致 |
| AC13 | 统一 Room 页 | 两端成员列表/进度一致；昵称可改、重名自动加后缀、本地记忆生效、可「忘记」 |
| AC14 | 版本门禁 | v1 页面连接 → 明确提示「请刷新」；旧端不静默失败 |
| AC15 | 零存储（v2） | `members`/`profile` 广播只进内存，零存储审计仍通过；日志不含显示名/roomId |

性能基线（记录用途，不设死线）：同 Wi-Fi 500MB ≤ 60 秒为达标，≤30 秒为优秀。

## 9. 术语

- **管理员（admin）**：创建房间的设备，房间生命周期与管理权（批准/移除/关房/邀请）由它掌握；阶段 2 可移交。
- **成员（member）**：通过二维码/链接/数字码加入房间的设备；可收发、可改名。
- **roomId**：16 字节随机标识，可公开。
- **roomKey**：32 字节会话根密钥，只在二维码/链接 fragment 或经 SAS 认证后的通道里出现。
- **显示名（name）**：设备的可编辑名称，默认 `平台 · 4 位代号`，房间内唯一，可本地记忆。
- **transfer**：一次 `manifest → accept → 分片 → done → ack` 的传输，用 `transferId` 标识；
  同一对设备同一时刻只有一条。
- **路径标签**：局域网直连 / 直连 / 中继，来自 ICE 选中候选对的类型。
- **SAS**：Short Authentication String，由双方 DTLS 指纹派生、人工比对的短串，本产品用 4 个 emoji 表示。
